The score formula is unchanged. What changes the strategy is who gets paid: SCORING_SYSTEM is "top", so only the first ten miners of a round are paid at all, on a fixed curve. That curve is a step function, which means a score gain that crosses no rank boundary pays nothing.

Consistency is quantised, and that is the whole game

Stage 4 fits a random forest per target under a five-fold split and combines the cross-validated scores. The detail that decides everything is arithmetic rather than biological: r2_score returns exactly 1.0 for a constant column predicted exactly, and normalized_mae returns the raw error unnormalised once the target's standard deviation falls below 1e-9.

consistency_factor = clamp(0.7 · max(avg_r2, 0) + 0.3 · (1 − avg_nmae))

The construction ladder

Miner._build tries these in order. Each falls through to the next on a decline, a short pool, a missing GPU or too little budget, so a failure anywhere lands on the build the miner had before that rung existed. Every builder signals a decline the same way — a null row set with a human-readable reason, never an exception and never an empty list — which is what makes the ladder safe to fall down.

Two constructions, one machine

All-cut and all-HDR are the same code with one string changed: the rule handed to the guide screen. Everything else — the bank, the min-union group, the conditional fill, the assembly — is shared. So the difference in what they pay is entirely a matter of how many targets the rule pins and over how many seeds it can hold them.

all-cut all-HDR {{ row.property }} {{ row.allCut }} {{ row.allHdr }}

Read the trade off the two middle rows. All-HDR pins three targets and takes a hit seed to exactly 1.0, but only over about 1.8 percent of the seed space. All-cut pins one target, worth 0.20 to 0.23, over 13 to 29 percent of it. All-HDR loses on the mean by roughly 24 points a round and ships anyway, because the payout curve pays placement rather than average.

Where a hotkey's window comes from

 } The seed-window prediction, and why it is free to be wrong

Since a spike needs a round seed inside a narrow band, predicting which part of the seed space a round will draw from would be worth money. The branch has two attempts at it, and both measure at chance.

The newest is a {{ seedModel.parameters | number }}-parameter transformer, one finetuned checkpoint per cell type, and its output is live and load-bearing: the three classes it names become the joined space the fleet tiles. Measured over {{ seedModel.testRounds }} walk-forward rounds, against its own committed evaluation:

The model beats neither, at p = {{ seedModel.pValue | number: '1.3-3' }} against the best reference, and its log loss of {{ seedModel.logLoss | number: '1.4-4' }} is worse than simply naming a uniform distribution, at {{ seedModel.uniformLogLoss | number: '1.4-4' }}. It learned to emit the uniform distribution, which is the correct answer to an unpredictable target.

Two traps in reading those numbers, both of which the branch's own prose falls into. The figures it quotes elsewhere come from an earlier run that appears in no committed artifact. And the chance baseline it compares against is mis-specified as 1.000: a round can draw the same class twice while the scorer caps a class at one hit, which happened on {{ seedModel.duplicateRounds }} of the {{ seedModel.testRounds }} test rounds, so true chance is {{ seedModel.chanceHits | number: '1.4-4' }}. That puts the model nominally above chance rather than below it. The verdict of no edge survives either way.

The older maximum-likelihood window model reaches the same null from the other direction: it fits a single balancing parameter, and that parameter comes out at exactly 0.00 for two of the four cell types, which means every window ties and its "rank 1" is a stable-sort tie-break to the lowest index rather than a prediction. Check that parameter before reading any rank as a forecast.

Running them anyway costs nothing, and that is a measured statement rather than an optimistic one: band position is free. Seeds are independent uniform draws, verified across all nine windows on HEK293, so concentrating hotkeys on a predicted window is exactly expected-value-neutral under a uniform generator. Three arbitrary classes are worth precisely as much as three others, and the prediction file accrues a scored record either way — so if the generator ever stops being uniform, the walk-forward number moves off chance first.

What would actually pay is a different problem, and nothing has measured it. The construction needs the seeds to within about 3 of {{ seedSpace }}; these models predict 100-seed windows. An oracle build pinned to two of a round's three seeds took rank 1 of 245, so the prize is real — but a blind band inside a correctly predicted window is worth roughly one chance in 2850.

The timing envelope

Every construction here is far too slow to build inside the presigned URL's {{ envelope.ttlSeconds }}-second life, so the build was moved off that path entirely. A round's task is published on a public, unsigned endpoint the moment the round opens, carrying the same contract the validator will hand over later — the only difference is the seed, which is 0 on both sides until the round closes. So the miner polls for the newest unstamped task, builds it on sight, and the deadline then only has to cover the upload.

What binds, and what it forces

Memory rather than the GPU. One seed-depend build holds enough that four concurrent builds would exhaust the box, which is why that build is shared: one process takes an exclusive lock, builds once, writes the rows outside the per-hotkey namespace, and the siblings load them. A follower that runs out of budget waiting must fall through the ladder rather than build its own copy — the whole point is that four concurrent builds do not fit.

Where the code lives

Two things to know before reading around in the branch. Its repo root holds 83 top-level Python scripts and 169 JSON result files, none of which either neuron imports — they are the research record, and the measurements quoted on this page come from them. And the generator imports the validator's own stage functions rather than reimplementing the scoring maths, which means editing a validation stage silently changes miner behaviour.
